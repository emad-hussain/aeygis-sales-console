## What "locally" means here

Only the **console frontend** runs on your machine. Everything it talks to is real,
deployed AWS:

| Piece | Where it runs |
|---|---|
| Internal console (React + Vite) | **your machine**, `localhost:5173` |
| Cognito, AppSync, DynamoDB, S3, Lambdas | deployed, `ca-central-1` |
| Public assessment form | the **live site**, a separate repo — see caveats |

There is no local emulator and none is wanted: Amplify Gen 2's development model is
a personal cloud sandbox, so what you test against is the real service behaviour
including its authorization rules. A local mock would agree with itself and
disagree with AWS.

### Two separate things, easily confused

- **`npm run console`** — starts the Vite dev server. Uses the already-deployed
  backend. **Safe, read/write against real data, no deploy.**
- **`npm run sandbox`** — starts Amplify's watcher, which *redeploys the backend*
  on file change. Only needed when changing anything under `amplify/`.
  **⛔ This is an AWS mutation and needs approval.**

You almost certainly want the first one.

## Seeded data, and what each record demonstrates

`npm run seed:demo` submits four assessments **through the real public mutation**,
SigV4-signed exactly as an anonymous browser would. It does not write to DynamoDB
directly, so seeding also exercises validation, consent enforcement and band
widening — anything it produces is something the live form could genuinely produce.

| Clinic | Demonstrates |
|---|---|
| Riverside Family Practice | **Bands only.** Lands as `needs_confirmation`; the pricing panel *refuses to quote* until exact counts are entered. This is the realistic default, because the live form only sends ranges. |
| Bayview Solo Clinic | **Micro/Starter overlap.** Both tiers apply and the console shows both — the approved docs resolve this by human judgement, so the tool presents the choice rather than making it. |
| Lakeshore Medical Group | **Professional with per-unit scaling.** 10 providers / 6 locations → setup $65,000 = $55,000 + 2×$2,000 + 2×$3,000. Train & Walk Away is correctly *absent*. |
| Northern Ontario Health Network | **Enterprise.** Pricing **refuses** and demands a discovery call. No price is shown, by design. |

Remove them all with `npm run cleanup:tests` (matches only known test addresses;
anything unrecognised is reported and left alone).

## Other useful commands

```bash
npm test                  # unit tests, no AWS, no credentials
npm run typecheck         # root
npm run lint:boundaries   # confidentiality barrier — a failure is an incident, not a nit
npm run check:synth       # synthesizes amplify/backend.ts and inspects the templates
npm run preview:proposal  # renders a real proposal PDF using your local Chrome
npm run check:layout      # proposal PDF page overflow, measured in a browser
npm run check:ui          # console layout/contrast/motion, 5 widths, real browser
npm run seed:demo         # 4 sample assessments via the real public path
npm run cleanup:tests     # remove test/demo records
```

`npm run preview:proposal` is the fastest way to see the client-facing document. It
uses your installed Chrome, runs the same template and the same client-safety
guards the Lambda runs, and writes `proposal-preview.pdf` plus the HTML beside it.

### `npm run check:synth` — run this before every deploy

`tsc` proves `amplify/backend.ts` compiles. It says nothing about what that file
*produces*, and the failures this project has actually hit there were all
synth-time or deploy-time: a circular dependency between the storage and function
stacks, a custom mutation colliding with an auto-generated one, IAM grants that
reached the wrong principal. Every one of those is visible in the synthesized
CloudFormation, and none of them is visible before running the synth.

This script builds the templates locally — **no AWS calls, nothing deployed** — and
asserts the properties that are easy to break silently:

- append-only models expose no `update`/`delete` mutations, and no mutation names collide
- every table requests the customer-managed key and point-in-time recovery
- no client-facing function can reach `proposals/internal/*`
- the unauthenticated role can read no `Assessment` fields
- `ses:SendEmail` is scoped to one named identity, never a wildcard

**It is a gate, not a guarantee.** CloudFormation still rejects things at deploy
time, and a policy that synthesizes perfectly can still deny at runtime — this
project has hit that more than once. Passing means "worth deploying", not "will work".

> One lesson from writing it, worth repeating for any check you add: nearly every
> assertion here is of the form *"X is absent"*, and those all pass on an empty
> list. The first version's schema regex matched nothing, so three checks reported
> a clean bill of health for a file it had never read. It now fails loudly if it
> parses zero mutations. **A check that cannot tell "nothing is wrong" from "I
> looked at nothing" is worse than no check**, because nobody investigates a pass.

### Verification against deployed AWS (needs credentials)

```bash
npm run verify            # guest access, browser signing, console roles, encryption
npm run verify:encryption # run after ANY deploy that adds a model — see below
```

incomplete.

project with no dev server of its own.

It now submits to **this backend and nowhere else**; the formsubmit.co email was removed
and `AEYGIS_API_ENDPOINT` is set. **The live site has not been deployed yet**, though, so
nothing reaches this backend from the real site. Use `npm run seed:demo` to populate the
console. (Pending item P12.)

## Gotchas that will waste your time

**Vite's dev server can serve code that is NOT on disk.** On this Windows
setup the watcher coalesces rapid successive writes and keeps a mid-edit
transform in its cache. It happened twice during the Porcelain rebuild:
`authTheme.ts` served the previous font stack while the file said Manrope, and
`App.tsx` served a new import with none of its usages. Nothing errors — the
page just renders older code, and any verification you run against it is
meaningless.

`npm run check:ui` now fails loudly on this before it runs anything else: it
compares the stylesheet the server sends against the file on disk, and checks
that every `className` literal in each `.tsx` survives into the served module.
If it trips, touch the files or restart `npm run console`.


**`pgrep` / `pkill` cannot see Windows processes.** `pgrep -f 'ampx sandbox'`
returns nothing even while a sandbox is running, so "confirmed nothing running" is
a false reading and `pkill` kills nothing. Orphaned watchers then accumulate until
esbuild dies with `fatal error: runtime: cannot allocate memory`. Use:

```powershell
@(Get-CimInstance Win32_Process -Filter "Name='node.exe'" |
  Where-Object { $_.CommandLine -like '*ampx.js*' }).Count
```

**Only one sandbox at a time.** A second instance fails with
`MultipleSandboxInstancesError`. Stop the previous one first — and verify it with
the command above, not with `pgrep`.

**Never pipe the watcher through `tail`.** `npm run sandbox | tail -25` produces no
output at all, because the pipe never flushes for a process that does not exit.

**After any deploy that adds a model, run `npm run verify:encryption`.** Amplify
ignores `kmsMasterKeyId` when it *creates* a table, so a new model lands on the
AWS-managed key while the template, the synth log and `describe-table` all report
success. Full detail in `deployment.md` → Gotcha 6.
