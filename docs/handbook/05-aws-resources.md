**Why `ca-central-1` and nothing else.** Canadian data residency is the product's core

the marketing says otherwise, and it would not announce itself.

The `default` AWS profile's region is `us-east-1` and is **deliberately left unchanged** —
it is used for unrelated work in this account. Region is pinned per command with
`cross-env AWS_REGION=ca-central-1` in every npm script instead. That is not just
convenience: the guard in `backend.ts` reads environment variables, so if region came from
`~/.aws/config` all three would be `undefined` and the guard would fall through to a
warning. Setting the env var explicitly is what upgrades the guard from "warns" to
"throws".

## 5.1 CloudFormation

### `CDKToolkit`

**What it is.** The CDK bootstrap stack: a staging S3 bucket, an ECR repository, five IAM
roles, and an SSM parameter recording the bootstrap version.

**What it does.** Holds the assets (Lambda bundles, layer archives, templates) that CDK
uploads before CloudFormation can deploy them, and provides the roles CDK assumes to do
the deploying.

**Why it was needed.** Nothing in this project can deploy without it. It is created once
per account-region pair.

**Without it.** `ampx sandbox` fails immediately with a bootstrap error.

### `amplify-aeygissalesplatform-EmadHussain-sandbox-b7b6a4ac77`

**What it is.** The root stack for the whole backend. Everything else is a nested stack
under it, except the resources with a `RETAIN` removal policy.

**How it fits.** Amplify generates nested stacks per resource category — `auth`, `data`,
`storage`, `function` — and `backend.ts` adds three more by hand:

| Custom stack | Created by | Holds |
|---|---|---|
| `Encryption` | `backend.createStack('Encryption')` | The customer-managed KMS key |
| `ChromiumPack` | `backend.createStack('ChromiumPack')` | The private bucket and CloudFront distribution serving the browser pack |
| `EmailDelivery` | `backend.createStack('EmailDelivery')` | The SES configuration set, event destination, and SNS topic |

**Why those three are separate stacks rather than nested inside a function's stack.**
Circular dependency. `storage` already depends on `function` because `allow.resource(fn)`
grants bucket access; referencing anything from the function stack back into storage
closes the loop and CloudFormation refuses:

```
CloudformationStackCircularDependencyError: circular dependency found
between nested stacks [storage, data, function]
```

A dedicated stack has no such edge.

## 5.2 Cognito

### User pool — `ca-central-1_RxZghEUxq`

**What it is.** The staff directory. Email-based sign-in.

**What it does.** Authenticates the internal console. Issues an ID token (carrying `sub`,
`email`, `cognito:groups`) and an access token (carrying `sub`, `cognito:groups`,
`username` — but **not** email).

**Why it was needed.** The console holds confidential client business information and can
send documents to clients. It needs real authentication with real, revocable identities.

**How it fits.** It is the default authorization mode for the whole AppSync API. Every
console call goes out as `authMode: 'userPool'`.

**Configuration notes.**

- `<Authenticator hideSignUp>` — **there is no self-registration.** Staff accounts are
  provisioned by an administrator. Open sign-up on an internal console holding client
  data would be an obvious hole.
- `multifactor` and `accountRecovery` are **deliberately omitted** for now. Their option
  shapes were not verifiable against current documentation, and guessing them would trade
  a real MFA policy for a plausible-looking one. Add them once the shapes are confirmed
  against the installed `.d.ts`. Tracked as an unverified claim in `PROJECT-STATUS.md`.
- The pool client enables `ALLOW_USER_SRP_AUTH`, which is why the verification scripts
  sign in via SRP through `aws-amplify` rather than an admin flow.

### Cognito groups — `contributor` (precedence 0), `approver` (precedence 1)

**What they are.** The entire role model.

**What they do.** Group membership is the *only* thing separating the two staff roles, so
promoting someone is a Cognito group change rather than a code change.

**How they fit.** Every model's authorization rule names them
(`allow.groups(['contributor','approver'])`), and the two privileged mutations name
`approver` alone.

**Important property.** Group membership is **mutable**, which is why `Approval` snapshots
the approver's groups at decision time instead of resolving them at read time. An audit
trail must not depend on current state.

**Also important.** Groups come from the ID token, so they reflect membership **at
sign-in**. A user added to `approver` mid-session must sign out and back in.

### Identity pool — `ca-central-1:b8b32869-dce2-4f64-b98c-de40483d886b`

**What it is.** Provisioned implicitly by `defineAuth`. Provides AWS credentials to both
signed-in and anonymous callers.

**What it does.** Two separate jobs:

1. **Anonymous:** issues short-lived, scoped credentials to the public assessment form, so
   `allow.guest()` on the `submitAssessment` mutation is resolvable. The browser does
   `GetId` → `GetCredentialsForIdentity` → SigV4-signed POST.
2. **Signed-in:** issues credentials that let the console read proposal PDFs directly from
   S3 with a presigned URL, bound by the storage rules.

**Why it was needed rather than an API key.** An API key is a bearer credential that would
have to ship in the public site's JavaScript, where anyone can read it and it never
expires. The identity pool's unauthenticated role is the documented production choice.

### IAM role — unauthenticated

`amplify-aeygissalesplatfo-amplifyAuthunauthenticate-0V6xlHSZ3NhD`

**This is the security control the entire public path depends on**, so its complete
permission set is recorded verbatim:

```json
{
  "Action": "appsync:GraphQL",
  "Resource": "arn:aws:appsync:ca-central-1:326629581669:apis/fuufxnavzfgshfme7635fq5obq/types/Mutation/fields/submitAssessment",
  "Effect": "Allow"
}
```

**One ARN.** No `Assessment` type ARNs. No `getAssessment`, no `listAssessments`, no
`createAssessment`. A guest cannot read assessment data because the policy contains no ARN
that would permit it — not because a rule says no.

**If this policy ever grows beyond that single statement, treat it as a security
regression.**

Verified by `scripts/verify-guest-access.mjs`, which obtains genuine anonymous credentials
and asserts 13 checks — including that every read operation is denied.

### IAM role — authenticated

`amplify-aeygissalesplatfo-amplifyAuthauthenticatedU-8cwSXVU07Z5Z`

The base signed-in role. The per-group roles below carry the actual data access.

### Cognito group roles — `contributor` and `approver`

**What they do.** Carry the S3 storage grants and, critically, the **KMS decrypt** grant.

**Why the KMS grant is here and not just the S3 grant.** This is the third occurrence of
the project's most expensive trap. The storage rule
`allow.groups(['contributor','approver']).to(['read'])` grants `GetObject` on
`proposals/client/*`, and the console's "View PDF" button correctly generated a presigned
URL using it — and every download 403'd anyway, with the real reason buried in the
response *body*, not the status code:

```
AccessDenied ... is not authorized to perform: kms:Decrypt
```

S3 read access and KMS decrypt access are **two separate grants**. See §5.5.

## 5.3 AppSync

### GraphQL API — `fuufxnavzfgshfme7635fq5obq` (`amplifyData`)

**What it is.** The single API surface. Everything — public and internal — goes through
it.

**What it does.** Hosts five models with generated CRUD resolvers, five custom
Lambda-backed mutations, and the authorization rules that gate them all.

**Why it was needed.** It is the boundary. Hiding a button in the console proves nothing;
this is where "a contributor may not approve" is actually enforced, before any Lambda
runs.

**Authorization modes:**

| Mode | Used by |
|---|---|
| `AMAZON_COGNITO_USER_POOLS` (default) | The console, every call |
| `AWS_IAM` | The public form (identity pool, unauthenticated) and every Lambda writing back through the API |

**No API key mode**, deliberately.

**Note on how Lambdas write.** The functions do not use the DynamoDB SDK directly for
model data. They call back through AppSync with `authMode: 'iam'`, which means the
**AppSync data-source role** is the principal that touches DynamoDB — not the Lambda's own
execution role. That distinction matters for KMS grants (§5.5).

### Data-source roles — `<Model>IAMRole`, e.g. `AssessmentIAMRole`

**What they are.** One IAM role per model, generated by Amplify, used by AppSync to read
and write that model's table.

**Why they matter here.** They are the principals that actually perform DynamoDB
operations, so they are the ones that need KMS access. `backend.ts` matches them by
pattern (`/IAMRole$/`) rather than by name so models added in later phases are covered
automatically — and **throws at synth** if the pattern matches nothing, because the
failure mode of a silently-missing grant is far worse than a broken build.

## 5.4 DynamoDB

Five tables, one per model. All `PAY_PER_REQUEST`. All on the customer-managed key. All
with point-in-time recovery.

| Table | Holds | Index — partition / sort | GraphQL query field |
|---|---|---|---|
| `Assessment-fuufxnavzfgshfme7635fq5obq-NONE` | Leads | `status` / `submittedAt` | `assessmentsByStatus` |
| | | `submitterIpHash` / `submittedAt` | `assessmentsBySubmitterIpHash` |
| `ProposalVersion-...` | Immutable priced versions | `assessmentId` / `createdAt` | `proposalVersionsByAssessment` |
| `Approval-...` | Immutable decisions | `proposalId` / `decidedAt` | `approvalsByProposal` |
| `AuditEvent-...` | The audit trail | `subjectId` / `occurredAt` | `auditEventsBySubject` |
| `ProposalDelivery-...` | Send attempts | `proposalId` / `sentAt` | `deliveriesByProposal` |

> The **physical** GSI names are generated by Amplify from the query field plus the sort key
> — the two verified against the live account are `assessmentsByStatusAndSubmittedAt` and
> `assessmentsBySubmitterIpHashAndSubmittedAt`. The query fields above come from the schema
> and are what the code actually calls.

**Why DynamoDB rather than a relational database.** The access patterns are all
key-and-range: "this lead", "versions for this assessment newest first", "decisions for
this proposal". There are no joins and no reporting queries. Serverless, per-request
billing, and no idle cost suits a system that handles a handful of proposals a month.

**Why `submittedAt` is an explicit field rather than the implicit `createdAt`.** Using a
system field as a GSI sort key requires declaring it, so the project owns that one
outright.

**Why the IP-hash index exists.** It backs per-IP rate limiting without a separate
throttle table. Reusing an index avoids provisioning infrastructure whose only job is
counting.

### Point-in-time recovery

**ENABLED on every table.** Gives a continuous 35-day restore window. Without it there is
no undo for a bad deploy or an erroneous delete.

### Deletion protection — deliberately OFF

It would block `npm run sandbox:delete`, and a sandbox is meant to be disposable. **Turn
it on for the branch environment when one is created.**

### ⚠ The trap that has now struck three times

**Amplify's tables are not `AWS::DynamoDB::Table`.** They are a custom
`Custom::AmplifyDynamoDBTable` resource. Two consequences:

1. `table.node.defaultChild` is `undefined`, so the normal CDK L1 escape hatch fails at
   synth with *"Cannot set properties of undefined"*. Overrides must go through
   `backend.data.resources.cfnResources.amplifyDynamoDbTables[modelName]`.
2. **Its provider ignores `kmsMasterKeyId` when it CREATES a table.** The table comes up
   KMS-encrypted but under the AWS-managed `alias/aws/dynamodb` key, and the CMK is only
   honoured on a later **update**.

The second is maximally deceptive. The CloudFormation template correctly requests the CMK.
The synth log says success. `describe-table` reports `SSEType: KMS, Status: ENABLED`.
**Every signal short of comparing the key ARN says it worked.**

This has hit `ProposalVersion` and `ProposalDelivery`. Both were remediated with:

```bash
aws dynamodb update-table --table-name <T> --region ca-central-1 \
  --sse-specification "Enabled=true,SSEType=KMS,KMSMasterKeyId=<cmk-arn>"
```

**`npm run verify:encryption` after any deploy that adds a model is mandatory, not
optional.** It compares actual key ARNs.

## 5.5 KMS

### `alias/aeygis-sales-platform-data`

ARN: `arn:aws:kms:ca-central-1:326629581669:key/53354d9a-0b47-41e3-b55f-63b4f886562a`

| | |
|---|---|
| **Manager** | `CUSTOMER` |
| **Rotation** | Enabled |
| **Removal policy** | **RETAIN** |

**What it is.** One customer-managed key protecting everything at rest: all five DynamoDB
tables and the proposals S3 bucket.

**Why it was needed.** DynamoDB always encrypts at rest, but by default with an
**AWS-owned** key. That is real encryption, and it gives us no key policy, no rotation
control, and no CloudTrail record of encrypt/decrypt calls. The Aeygis Cloud Migration
Framework sells "KMS AES-256 encryption" to clients — with an AWS-owned key, that claim
and the configuration do not match. A customer-managed key closes the gap and makes the
claim auditable.

**Why `RETAIN`.** Destroying the key would make every encrypted item permanently
unreadable, **including anything restored from a backup**.

**Cost note.** Unlike the AWS-owned key, a CMK bills per API call and counts against KMS
quotas. DynamoDB caches the decrypted table key for five minutes and the S3 bucket has
`bucketKeyEnabled: true`, so real call volume is low — but it is no longer free.

### ⚠ The three-role-family trap — read this before touching encryption

**This has cost a real incident four separate times.** The pattern is always the same: an
S3 or DynamoDB permission is necessary but **not sufficient** when the data is
KMS-encrypted. Decrypt is a *separate* grant, and three of the four failed silently at
configuration time and only broke at runtime.

| # | Principal | If the grant is missing |
|---|---|---|
| 1 | `AmplifyManagedTable(OnEvent\|IsComplete)Role` | The **deploy rolls back** on `kms:DescribeKey`. Loud — the only one of the four that fails loudly. |
| 2 | `<Model>IAMRole` (AppSync data source) | The deploy **succeeds**, encryption reports `ENABLED`, admin writes work — **and every application write fails at runtime.** This broke intake after the first successful CMK deploy. |
| 3 | Lambda execution roles that touch S3 **directly** | Deploy succeeds; the first S3 read or write from that function throws `AccessDenied`. |
| 4 | Cognito `contributor` / `approver` group roles | **The one that took longest to notice.** The console's "View PDF" generated a presigned URL successfully — `getUrl()` has no way to know decrypt will fail — and the download 403'd with the reason buried in the S3 XML error body, not the status code. |

**Lambda roles that reach data only through AppSync do NOT need this.** The *data-source*
role (row 2) is the principal that touches DynamoDB there. Rows 3 and 4 are different:
those principals talk to S3 directly.

**Two further facts, both established by inspecting deployed policy rather than assumed:**

- **A key policy naming the account root does not grant access.** It only delegates
  authority to IAM, so each principal still needs an identity-based policy. Hence explicit
  per-role grants.
- **CDK's `grantEncryptDecrypt` produces exactly** `kms:Decrypt`, `kms:Encrypt`,
  `kms:ReEncrypt*`, `kms:GenerateDataKey*`. It does **not** include `DescribeKey` or
  `CreateGrant`, both of which DynamoDB requires. They are granted explicitly. An earlier
  revision claimed otherwise in a comment and was wrong.

**Who holds what today:**

| Principal | Grant | Why exactly that |
|---|---|---|
| `dynamodb.amazonaws.com` (service principal) | encrypt + decrypt, via the key's resource policy | A service principal has no identity policy to attach to |
| Table-manager roles (matched by pattern) | encrypt/decrypt + `DescribeKey` + `CreateGrant` | Amplify's custom-resource provider calls `DescribeKey` while applying the setting |
| Data-source roles (matched by pattern) | encrypt/decrypt + `DescribeKey` + `CreateGrant` | They perform the actual table reads and writes |
| `price-proposal`, `render-proposal-pdf`, `decide-proposal` | encrypt/decrypt + `DescribeKey` | They read and write S3 objects directly |
| `send-proposal-email` | **decrypt only** + `DescribeKey` | It reads two objects and writes none. Granting encrypt would be a permission with no call site, on the one function whose output leaves the building. |
| `contributor` / `approver` group roles | decrypt + `DescribeKey` | The browser reads the PDF directly via a presigned URL |
| `delete-proposal-version` | **nothing — deliberately** | Its only S3 action is `DeleteObject`, which neither encrypts nor decrypts. Its DynamoDB work goes through AppSync. Verified by actually deleting a version against real AWS, not assumed. |

That last row is deliberate and documented in `backend.ts` at length, because
over-granting a key to a function that provably does not need it is its own quiet failure.

## 5.6 S3

### Proposals bucket — `amplify-aeygissalesplatfo-aeygisproposalsbucket04e-qwmr0tl5iuep`

**What it is.** The document store. Three prefixes with deliberately different reach.

| Prefix | Contents | Who can read | Who can write |
|---|---|---|---|
| `snapshots/` | Frozen, client-safe JSON. **The only input to the renderer.** | staff, `price-proposal`, `render-proposal-pdf`, `decide-proposal`, `send-proposal-email` | `price-proposal` only (`delete-proposal-version` may delete) |
| `proposals/client/` | The rendered client-facing PDFs | staff, `render-proposal-pdf`, `send-proposal-email` | `render-proposal-pdf` only (`delete-proposal-version` may delete) |
| `proposals/internal/` | Internal-only material (margin working, cost notes) | **approvers only** + `price-proposal` | `price-proposal` only |

**The split is confidentiality barrier 4 of 5.** `render-proposal-pdf` and
`send-proposal-email` have **no ARN at all** for `proposals/internal/*` — not a deny, an
absence. They cannot read internal material even if a future code change tried to.
Asserted by `npm run check:synth`.

**There is no `allow.guest` anywhere in the storage rules.** Public users get zero S3
access.

**Configuration applied in `backend.ts`:**

| Setting | Value | Why |
|---|---|---|
| Versioning | **Enabled** | Regenerating a proposal writes to the same key. A client may already hold the previous PDF, so the prior bytes must survive for the approval trail to mean anything. |
| Encryption | `aws:kms` with the project CMK, `bucketKeyEnabled: true` | Bucket keys cut KMS request volume sharply by reusing a data key per prefix, which matters because a CMK bills per call. |
| Lifecycle | Expire noncurrent versions after 365 days, keeping the newest 10 | So the audit trail does not grow without bound. 365 days comfortably exceeds any live sales cycle. |
| `keepOnDelete` | `true` | The bucket **survives `ampx sandbox delete`** on purpose — generated proposals and their approval trail should not vanish with an ephemeral dev stack. |
| Object Lock (WORM) | **OFF**, deliberately | Confirmed with the user. It can only be set at bucket creation, so turning it on later requires a new bucket and a data migration. Recorded as a deferred decision. |

**A note on the versioning/deletion interaction.** Because versioning is on,
`DeleteObject` writes a delete marker rather than destroying bytes. Discarding a draft
version therefore makes its snapshot and PDF return 404 to normal reads while the prior
object versions remain until the lifecycle rule expires them. The delete-version function
documents this plainly rather than describing itself as an erase.

**Note on `defineStorage`.** It exposes no versioning property, so `backend.ts` drops to
the L1 `CfnBucket` via `node.defaultChild`. That escape hatch **does** work here, unlike
for DynamoDB, because the bucket really is a native `AWS::S3::Bucket`.

### Chromium pack bucket — `amplify-aeygissalesplatfo-chromiumpackbucketf471e0-hnuzb4xinhse`

**What it is.** A separate, private bucket holding exactly one object:

```
chromium/chromium-v149.0.0-pack.x64.tar     69,642,240 bytes
```

**What it does.** Serves the ~66 MB headless-browser binary that `render-proposal-pdf`
downloads on a cold start.

**Why it is a separate bucket.** It holds a build artifact, never client data. Adding a
publicly-reachable prefix next to confidential proposals would be the wrong shape.

| Setting | Value |
|---|---|
| Public access | `BlockPublicAccess.BLOCK_ALL` |
| Encryption | SSE-S3 (not the CMK — this is not client data) |
| SSL | Enforced |
| Removal policy | RETAIN |

## 5.7 CloudFront

### Chromium pack distribution — `dhediy6ipw02c.cloudfront.net`

**What it is.** A CloudFront distribution with **Origin Access Control** in front of the
private Chromium bucket. Price class `PRICE_CLASS_100` (North America only).

**Why it exists, and why not a presigned URL.**

`@sparticuz/chromium-min` fetches its browser pack with a **plain, unauthenticated
`fetch(url)`** — verified by reading the installed package's own source
(`node_modules/@sparticuz/chromium-min/build/helper.js`):

```js
const response = await fetch(url, { redirect: "follow", signal: AbortSignal.timeout(300_000) });
```

No SigV4 signing, no headers. So an S3 URL the function's IAM role can read is **not
sufficient** — the URL must be fetchable with zero credentials.

A presigned URL would satisfy that today and then **silently expire later**.
`chromium-min` only refetches on a **cold start**, so it would work for days or weeks and
then begin failing with no code change and no warning. That is the wrong shape for a value
living in a Lambda environment variable indefinitely, even though it looks like the more
locked-down choice.

**Why not just make the object public.** This account has S3 Block Public Access enabled
at the **account level**, all four settings (checked with
`aws s3control get-public-access-block` before deciding). Loosening that would be an
account-wide posture change to solve a one-object problem.

CloudFront + OAC gives a plain, credential-free HTTPS URL without touching that setting at
all.

**Why the version is pinned in the path.** `layers/chromium/VERSION` records that the pack
**must** match `@sparticuz/chromium-min@149.0.0` exactly — a mismatched pack fails
obscurely at browser launch rather than with a clear error. A version-qualified path makes
a future bump land at a new URL rather than overwriting the old one underneath a cached
CloudFront response.

`CHROMIUM_PACK_URL` is derived at synth time from
`chromiumPackDistribution.distributionDomainName` and **never hand-typed**.

**Deploy note.** Creating this distribution takes **5–15 minutes** — noticeably slower
than the rest of an Amplify deploy.

## 5.8 Lambda

Six functions. Full behaviour in [Backend functions](06-backend-functions.md); this is the
infrastructure view.

| Function | Runtime | Memory | Timeout | Why sized that way |
|---|---|---|---|---|
| `submit-assessment` | nodejs22.x | 256 MB | 30 s | Was 15 s while it was a validate-and-put with no external calls. It now also sends the new-lead notification via SES, and a 15-second budget shared between a rate-limit query, a DynamoDB write and an SES call leaves no room for a slow one — a timeout would fail a submission that had already been stored. |
| `price-proposal` | nodejs22.x | 512 MB | 30 s | Reads a record, prices, writes an S3 object and a row, fires an async invoke. |
| `render-proposal-pdf` | nodejs22.x | **2048 MB** | **60 s** | From the `@sparticuz/chromium` docs, not guessed: ≥512 MB works, 1600+ MB recommended. **More memory also means more CPU, so a larger setting is often cheaper** — brotli extraction and browser launch finish sooner. Timeout ≥10 s for a cold start, 30 s recommended; 60 s here for headroom. |
| `decide-proposal` | nodejs22.x | 512 MB | 30 s | Reads a version, re-hashes an S3 object, writes two records. |
| `delete-proposal-version` | nodejs22.x | 512 MB | 30 s | Reads a version and its decisions, deletes two objects and a row, writes one audit record. |
| `send-proposal-email` | nodejs22.x | 512 MB | 30 s | Reads a JSON snapshot and a ~300 KB PDF, calls SES, writes two records. |

**The odd one out: `render-proposal-pdf` uses `defineFunction(provider)`, not plain
`defineFunction`.**

`@sparticuz/chromium-min` must be **external** to the esbuild bundle. It resolves the
browser binary through relative paths, so bundling relocates it and it fails at runtime
with the library's own message: *"you must externalize @sparticuz/chromium so it is not
relocated."*

This is not hypothetical. The first deploy used plain `defineFunction`, and downloading
the resulting package showed the library's guard text inlined into `index.mjs` (so it
**was** bundled) and exactly two files in the archive (so `./assets` was **not** shipped).

Amplify cannot express externalization. Verified in the installed types:

```ts
export type FunctionBundlingOptions = { minify?: boolean };
```

That is the whole type. So the documented provider overload is the only route, giving
direct control of esbuild via CDK's `NodejsFunction`.

**Consequences of the provider overload — read before editing that function:**

`ProvidedFunctionProps` exposes only `resourceGroupName`, so **Amplify does not manage
this function's name or environment**. Two follow-ons:

1. The generated `$amplify/env/render-proposal-pdf` module is not reliably produced, so
   the handler reads `process.env` directly and validates what it needs.
2. Environment variables are wired in `backend.ts` via `addEnvironment`.

### Lambda layer — `ChromiumLayer<8-char-content-hash>`

**What it is.** A layer carrying the `@sparticuz/chromium-min` **loader** and its 18
transitive dependencies. It does **not** carry the browser binary — that comes from
CloudFront at runtime.

**Why the content hash is in the construct id.** `AWS::Lambda::LayerVersion` is immutable,
so changing its content is a **replacement**-type update — and Amplify's sandbox deploys
with `--disable-rollback`, where CloudFormation refuses those outright:

```
Replacement type updates not supported on stack with disable-rollback.
```

Hit for real when the layer gained chromium-min's transitive dependencies. Putting the
hash in the construct id makes new content a **new logical resource**, so CloudFormation
does create-then-delete instead of replace-in-place, which it permits. Hand-renaming the
construct works once and is then forgotten.

**Why the layer is built with `npm install`, not a directory copy.** The first layer was a
`cp -r` of `node_modules/@sparticuz/chromium-min`. It deployed, the module resolved, and
the function died at runtime:

```
Cannot find package 'tar-fs' imported from
```

chromium-min pulls in 18 packages; the hand-copy shipped one. `npm run build:layer` now

### Why the fonts and logos are imported, not read from disk

The renderer originally did `readFileSync(join(dirname, 'assets', ...))`. Inspecting the
**actually deployed** package showed it contained exactly two files: `index.mjs` and
`index.mjs.map`. Amplify's bundler does not copy sibling asset directories, so every font
and logo was absent and the first render would have thrown `ENOENT`.

They are now baked into `template-assets.generated.ts` as base64 constants, so esbuild
inlines them into the bundle. That is a deliberate trade: about 130 kB of base64 in the
bundle in exchange for the assets being impossible to lose. Regenerate with
`npm run gen:assets`.

## 5.9 SSM Parameter Store

### `IP_HASH_SALT` (SecureString)

**What it is.** A 32-byte random secret, set via `npx ampx sandbox secret set IP_HASH_SALT`
and injected into `submit-assessment` by Amplify's `secret()` helper.

**Why it must be a real secret.** IPv4 space is only about 4 billion addresses, so an
unsalted or publicly-known-salt hash is reversible by brute force in minutes. That would
turn `submitterIpHash` into stored personal information rather than the privacy measure it
is meant to be.

**What happens if it is missing.** The handler **refuses to hash** and skips rate limiting
instead, logging an error. Failing open rather than pretending to protect something.

### `/aeygis-sales-platform/render-proposal-pdf/proposals-bucket-name`

**What it is.** A plain string parameter holding the proposals bucket name.

**Why it exists.** `render-proposal-pdf` uses the provider overload, so Amplify's automatic
SSM environment injection does not reach it — its deployed `AMPLIFY_SSM_ENV_CONFIG` ships
as an empty `{}`. Confirmed by reading the deployed configuration of all three functions:
`price-proposal` and `decide-proposal` correctly list a path to
`AEYGIS_PROPOSALS_BUCKET_NAME`; `render-proposal-pdf` does not.

**Why a new parameter rather than Amplify's own.** Amplify's parameter already exists and
already has the right value, but its path embeds the sandbox identifier
(`EmadHussain-sandbox-b7b6a4ac77`), which differs per developer and per environment.

**Why the IAM grant is built from a formatted ARN string.** Using the `StringParameter`
construct's own `.parameterArn` would import a value **from storage's stack** into the
function's policy, recreating exactly the circular dependency that passing
`bucket.bucketName` caused. A same-account/same-region ARN string built with
`stack.formatArn(...)` has no such dependency — it is synthesized independently in every
stack from that stack's own pseudo parameters.

**How the handler uses it.** Reads it once per **cold start** and caches it at module
scope. A warm container reuses the value.

**⚠ Never pass a bucket name to a function via `addEnvironment`.** `storage` already
depends on `function` because `allow.resource(fn)` grants bucket access; referencing
`bucket.bucketName` from the function stack points the arrow back and the deploy fails
with `CloudformationStackCircularDependencyError`.

## 5.10 SES

### Email identity — `rajaemadhussain@gmail.com`

| | |
|---|---|
| **Type** | Email **address** identity (not a domain) |
| **Status** | `VerificationStatus: SUCCESS` |
| **Role** | Both sender **and** recipient while in the sandbox |
| **DKIM** | `DkimSigning: False`, `DkimStatus: NOT_STARTED` |

**Created by hand, deliberately NOT declared in CDK.** `aws-cdk-lib/aws-ses` has an
`EmailIdentity` construct and it is tempting to declare the sender here. It is left out on
purpose, for two reasons:

1. **Creating an identity sends a verification email a human must click.** CDK can create
   the resource but cannot finish it, so an "as code" identity is only ever half-declared:
   it exists and does not work until somebody acts out of band.
2. **Verifying an identity is an AWS action this project requires explicit per-action
   permission for.** Folding it into a deploy would perform that action as a side effect
   of approving something else.

The identity is referenced in `backend.ts` **by ARN only**. If it does not exist, sends
fail with a clear SES error rather than the stack failing to deploy.

### Configuration sets — two, deliberately

| Set | Used by | Why separate |
|---|---|---|
| `aeygis-proposal-delivery` | `send-proposal-email` | Client-facing delivery reputation |
| `aeygis-internal-notifications` | `submit-assessment` | Internal new-lead heads-up |

Both publish the same four problem events to the same SNS topic. They are kept apart so a
bounce on our own inbox does not land in the reputation metrics that describe whether
**proposals reach clinics** — the number that actually matters commercially.

### Configuration set — `aeygis-proposal-delivery`

**What it is.** A named SES configuration set with **reputation metrics enabled**.

**What it does.** Every send passes `ConfigurationSetName`, which routes delivery events to
the SNS topic below and keeps proposal-delivery reputation measurable on its own rather
than mixed into any future account-wide sending.

**Why the name is pinned to a constant.** If CloudFormation generated the name, the
function would name one string and the deployed set would be another, and **every send
would fail** with a configuration-set-not-found error that reads like a service problem.
The name lives in `send-proposal-email/resource.ts` as an exported constant and
`backend.ts` imports it.

**TLS is left at the default (opportunistic), not `REQUIRE`.** `REQUIRE` refuses to deliver
to a mail server that will not negotiate TLS, and a clinic on an older mail host would
silently stop receiving proposals. That is a real trade-off rather than an oversight —
worth revisiting once the recipients are known.

### Event destination → SNS

Publishes exactly four event types:

```
BOUNCE · COMPLAINT · REJECT · DELIVERY_DELAY
```

**Not** `SEND`, `DELIVERY`, `OPEN` or `CLICK`. The CDK default is *all* event types, which
would publish a notification for every successful send — noise that trains people to
ignore the topic, which is worse than not having one.

`DELIVERY_DELAY` is included because a delayed message is a problem that has not finished
happening yet: it is the signal that arrives *before* a bounce.

## 5.11 SNS

### Topic — `ProposalEmailEvents`

**What it is.** Where bounces and complaints go.

**Why it was built BEFORE the first send, not after.** Two reasons:

1. The SES production-access request asks whether you handle bounces and complaints.
   Having it already working strengthens the request.
2. **In the sandbox, a bounce against your own test address lands that address on the
   account-level suppression list**, after which sends fail for reasons that look nothing
   like the cause. That is a classic lost morning.

**Topic policy.** Allows only `ses.amazonaws.com` to publish, conditioned on
`AWS:SourceAccount` and the configuration-set ARN. **Written by the CDK construct
automatically** — verified by reading the installed construct's source, because the SES
documentation describes adding that policy by hand and following it would have produced a
second, redundant statement.

**No subscription is created IN CODE — but one exists.** Subscribing an address sends a
confirmation email a human must click, so CDK can create the resource and cannot finish
it; the same reasoning that keeps the email identity out of CDK. It is therefore created
by hand and recorded here.

| | |
|---|---|
| Endpoint | `rajaemadhussain@gmail.com` |
| Protocol | `email` |
| Status | **Confirmed** — `PendingConfirmation: false`, re-verified 2026-08-26 |
| Created | 2026-08-23, by hand |

Both configuration sets publish here, so this one subscriber receives bounces and
complaints from **both** client-facing proposal delivery and internal notifications.

**It changes at the domain cutover.** A personal Gmail is the right answer while the
sender is also a personal Gmail; once `aeygis.com` is verified it should become a
monitored Aeygis address. See [Running in production](13-running-in-production.md).

## 5.13 What is deliberately NOT in this account

| Not present | Why |
|---|---|
| **VPC / NAT Gateway** | Nothing needs private networking. A NAT Gateway is the classic source of a standing hourly charge in an otherwise serverless stack. |
| **Provisioned concurrency** | Rendering is asynchronous and off the request path, so a cold start costs nobody anything. Provisioned concurrency would be the genuinely expensive choice. |
| **API Gateway** | AppSync is the only API surface. |
| **RDS / any always-on compute** | No relational access patterns, no idle cost wanted. |
| **An Amplify Hosting app** | The console is not hosted yet — it runs locally. Creating one needs approval and a decision about who can reach it. |
| **SES domain identity** | Blocked on `aeygis.com` DNS access. This is the single thing standing between the system and real-world deliverability. |
| **An SCP or region deny policy** | Raised with the user and **declined** (2026-08-23). Region residency remains a best-effort guard. |

**There should be no standing hourly charge in this stack.** If one appears, something was
created outside `amplify/`.

## 5.14 Cost

At sales volume — a handful of proposals a month — everything here is effectively free,
well inside AWS free tiers, with four things worth watching:

| Item | Why it costs |
|---|---|
| **KMS** | A CMK bills **per API call**, unlike the AWS-owned key. Mitigated by DynamoDB's 5-minute table-key cache and S3 bucket keys. |
| **`render-proposal-pdf`** | Runs at 2048 MB, billed per GB-second. The cold start is the expensive part. Async by design, so no provisioned concurrency. |
| **S3 versioning** | Retains every prior object version. The lifecycle rule (10 newest, 365 days) is what keeps this bounded. |
| **CloudFront** | One 66 MB object, fetched only on Lambda cold starts, `PRICE_CLASS_100`. Negligible, but not zero. |
