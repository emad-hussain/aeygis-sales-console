## 12.1 The short version

```bash
cd d:\Aeygis-Work\aeygis-sales-platform
npm install          # once
npm run console      # → http://localhost:5173
```

Sign in with a test user from `.test-credentials.json`. If the queue is empty, run
`npm run seed:demo`.

**That is it.** No AWS credentials are needed to run the console itself — only for the
verification and seeding scripts.

---

## 12.2 What "locally" actually means

Only the **console frontend** runs on your machine. Everything it talks to is real,
deployed AWS.

| Piece | Where it runs |
|---|---|
| Internal console (React + Vite) | **Your machine**, `localhost:5173` |
| Cognito, AppSync, DynamoDB, S3, all six Lambdas, SES | **Deployed**, `ca-central-1` |
| The public assessment form | **The live site**, a separate repository — see §12.8 |

**There is no local emulator and none is wanted.** Amplify Gen 2's development model is a
personal cloud sandbox, so what you test against is real service behaviour including its
authorization rules. A local mock would agree with itself and disagree with AWS.

### Two commands, easily confused

| | What it does | Needs approval? |
|---|---|---|
| **`npm run console`** | Starts the Vite dev server against the **already-deployed** backend. Read/write against real data, **no deploy.** | ❌ No |
| **`npm run sandbox`** | Starts Amplify's watcher, which **redeploys the backend** on every file change. | ⛔ **Yes — this is an AWS mutation** |

**You almost certainly want the first one.** You only need `sandbox` when changing something
under `amplify/`.

The backend **persists independently of any watcher.** You do not need `npm run sandbox`
running to use the console.

## 12.4 Signing in

Three test users exist. **There is no self-registration** — `<Authenticator hideSignUp>`,
and accounts are provisioned by an administrator.

| User | Group | What you should see |
|---|---|---|
| `test-contributor@aeygis-test.invalid` | `contributor` | Read and edit leads, fill discovery, see pricing, generate versions, discard drafts. **No Approve, Reject or Send buttons.** |
| `test-approver@aeygis-test.invalid` | `approver` | Everything above **plus** Approve / Reject / Send to client. |
| `test-nogroup@aeygis-test.invalid` | *(none)* | Signs in successfully, then **cannot read anything** — a read-only banner and an empty queue. |

**That third account is worth trying deliberately.** It demonstrates that authentication is
not authorization, and that the API refuses rather than the UI merely hiding controls.

Passwords are in `.test-credentials.json`. Manage the users with `npm run cleanup:users`
(which only ever touches usernames on its explicit list, and reports anything else rather
than guessing).

## 12.5 Seeded data, and what each record demonstrates

```bash
npm run seed:demo        # ⛔ writes to AWS — needs approval
```

**It submits four assessments through the REAL public mutation**, SigV4-signed exactly as an
anonymous browser would. It does **not** write to DynamoDB directly, so seeding also
exercises validation, consent enforcement, the honeypot and band widening — anything it
produces is something the live form could genuinely produce.

| Clinic | Demonstrates |
|---|---|
| **Riverside Family Practice** | **Bands only.** Lands as `needs_confirmation`; the pricing panel *refuses to quote* until exact counts are entered. This is the realistic default, because the live form only sends ranges. |
| **Bayview Solo Clinic** | **The Micro/Starter overlap.** Both tiers apply and the console shows both — the approved documents resolve this by human judgement, so the tool presents the choice rather than making it. |
| **Lakeshore Medical Group** | **Professional with per-unit scaling.** 10 providers / 6 locations → setup $65,000 = $55,000 + 2×$2,000 + 2×$3,000. Train & Walk Away is correctly **absent**. |
| **Northern Ontario Health Network** | **Enterprise.** Pricing **refuses** and demands a discovery call. No price is shown, by design. |

All use `@aeygis-test.invalid` — a **reserved TLD**, so no mail can ever be delivered to
them.

Remove them with `npm run cleanup:tests`, which matches only known test addresses; anything
unrecognised is reported and **left alone**.

## 12.6 A tour worth taking

1. Sign in as **contributor**. Open *Riverside* — note the amber warning that the prospect
   submitted ranges, and that pricing is blocked.
2. Enter `providers = 6`, `locations = 3`, tick **counts confirmed**, Save. Pricing appears;
   status moves `needs_confirmation → in_review`.
3. Open *Northern Ontario* — pricing refuses outright with the discovery-call requirement.
   The $150k–$450k figure is labelled internal guidance, not a quote.
4. Open *Bayview* — two tiers offered side by side.
5. Back on a priced lead, click **Generate**. A version appears in the Approval panel;
   "View PDF" turns up a few seconds later once Chromium finishes.
6. Sign out, sign in as **approver**. Approve / Reject now appear. Approve a version — note
   the message: *"Delivery is a separate, explicit step."*
7. The **Send to client** block appears below. Note it arms on the first click.
8. Sign in as **nogroup** — everything is denied, with an explanation.

## 12.7 Every command

### Free — local only, no AWS, no approval needed

```bash
npm test                  # 315 unit tests
npm run typecheck         # tsc --noEmit at the root
npm run lint:boundaries   # the confidentiality barrier — a failure is an incident, not a nit
npm run check:synth       # synthesizes backend.ts locally and inspects the CloudFormation
npm run preview:proposal  # renders a real proposal PDF with your local Chrome
npm run check:layout      # measures every proposal page for overflow, in a browser
npm run check:ui          # console layout, contrast and motion - 5 widths, both themes
                          #   NEEDS the dev server running AND leads in the queue;
                          #   run seed:demo first if cleanup:tests emptied it
npm run console           # the dev server
npm --workspace @aeygis/console run build
```

### ⛔ Touches AWS — each needs explicit permission

```bash
npm run sandbox           # deploys the backend, then watches for changes
npm run sandbox:delete    # DESTROYS the stack (the S3 bucket survives — keepOnDelete)
npm run bootstrap         # one-time CDK bootstrap
npm run secret:salt       # sets IP_HASH_SALT
npm run seed:demo         # writes four real assessments
npm run cleanup:tests     # deletes test records
npm run cleanup:users     # deletes test Cognito users
npm run verify            # 4 scripts: guest access, browser signing, console roles, encryption
npm run verify:console    # console role permissions only
npm run verify:encryption # compares actual KMS key ARNs
npm run verify:email      # ⛔ SENDS A REAL EMAIL
npm run resend -- <id> <v># ⛔ SENDS A REAL EMAIL
```

### The two most useful before a deploy

**`npm run preview:proposal`** is the fastest way to see the client-facing document. It uses
your installed Chrome, runs the same template and the same client-safety guards the Lambda
runs, and writes `proposal-preview.pdf` plus the HTML beside it.

**`npm run check:synth`** — run this before every deploy.

`tsc` proves `amplify/backend.ts` compiles. It says nothing about what that file *produces*,
and the failures this project has actually hit there were all synth-time or deploy-time: a
circular dependency between the storage and function stacks, a custom mutation colliding
with an auto-generated one, IAM grants that reached the wrong principal. Every one of those
is visible in the synthesized CloudFormation, and none of them is visible before running the
synth.

It builds the templates locally — **no AWS calls, nothing deployed** — and asserts:

- Append-only models expose no `update`/`delete` mutations, and no mutation names collide
- Every table requests the customer-managed key and point-in-time recovery
- No client-facing function can reach `proposals/internal/*`
- The unauthenticated role can read no `Assessment` fields
- `ses:SendEmail` is scoped to one named identity, never a wildcard, and covers the
  configuration set
- The bounce topic is not world-publishable

**It is a gate, not a guarantee.** CloudFormation still rejects things at deploy time, and a
policy that synthesizes perfectly can still deny at runtime — this project has hit that more
than once. Passing means *"worth deploying"*, not *"will work"*.

## 12.8 Running the public assessment form locally

It is hand-written static files, so any static server will do:

```bash
npm run site        # serves the website repo on http://localhost:8080
```

Then open <http://localhost:8080/assessment.html>.

> ⛔ **It must be served over `http://`. Do NOT open the file directly.**
>
> `file://` is not a *secure context*, so `crypto.subtle` is undefined — and the submission
> is SigV4-signed with it. The page will load and look completely normal, and every
> submission will fail. `http://localhost` **is** a secure context, which is why serving it
> works and double-clicking it does not.

**A submission from here is real.** It reaches the deployed API, writes a real `Assessment`,
and appears in the console. It also sends a new-lead notification unless the contact address
ends in `.invalid` — see [Backend functions](06-backend-functions.md). Use a `.invalid`
address when you are only exercising the form.

`npm run verify:local-site` proves this path works **without writing anything**: it serves
the site, runs the shipped submission code in a real browser against real Cognito and
AppSync, and submits **without consent** so the backend refuses before storing. A CORS or
signing failure looks completely different from that refusal, so the check cannot pass for
the wrong reason.

Verified 2026-08-26: secure context ✓, `crypto.subtle` ✓, Cognito and AppSync both return
`Access-Control-Allow-Origin: *` for a localhost origin ✓, signature accepted ✓.

## 12.9 What does NOT work locally, and why

**Sending email to anyone but the one verified address.** SES is in the sandbox. Any other
recipient is recorded as `blocked` with the reason visible in the console. That is the guard
working, not a fault.

**A hot-reloading dev server for the public site.** It is plain static files with no build
step, so there is nothing to `npm run dev` — edit a file and refresh.

**Nothing else.** PDF rendering, email delivery and the full pipeline all work.

> **The console's queue may be empty.** `npm run cleanup:tests` clears the seeded demo
> leads. `npm run seed:demo` puts four back — an AWS write, so it needs approval.

## 12.10 Gotchas that will waste your time

### Vite's dev server can serve code that is NOT on disk

On this Windows setup the watcher coalesces rapid successive writes and keeps a mid-edit
transform in its cache. It happened twice during the console rebuild: `authTheme.ts` served
the previous font stack while the file said Manrope, and `App.tsx` served a new import with
none of its usages.

**Nothing errors — the page just renders older code, and any verification you run against it
is meaningless.**

`npm run check:ui` now fails loudly on this **before it runs anything else**: it compares the
stylesheet the server sends against the file on disk, and checks that every `className`
literal in each `.tsx` survives into the served module. If it trips, touch the files or
restart `npm run console`.

### `pgrep` and `pkill` cannot see Windows processes

Git Bash cannot read Windows process command lines, so `pgrep -f 'ampx sandbox'` returns
**zero matches even while a sandbox is running** — and `pkill -f` kills nothing. Verified
directly by starting a sandbox and testing the patterns.

This silently accumulated **28 orphaned processes** in one session (nine of them
`ampx sandbox`), which exhausted memory and made esbuild die with
`fatal error: runtime: cannot allocate memory` — a failure that looks like a code problem and
is not.

**Every "confirmed nothing is running" based on `pgrep` was false.** Use PowerShell, and note
the `@(...)` — a single object has no `.Count`:

```powershell
$p = @(Get-CimInstance Win32_Process -Filter "Name='node.exe'" |
       Where-Object { $_.CommandLine -like '*ampx.js*' })
Write-Output "running: $($p.Count)"
foreach ($x in $p) { Stop-Process -Id $x.ProcessId -Force }
```

### Only one sandbox at a time

A second instance fails with `MultipleSandboxInstancesError` / `ConcurrentReadLock` over
`.amplify/artifacts/cdk.out`. Stop the previous one first — and verify it with the command
above, not with `pgrep`.

### Never pipe the sandbox watcher through `tail` or `head`

```bash
npm run sandbox | tail -25     # produces NO OUTPUT AT ALL
```

The pipe never flushes for a process that does not exit. Redirect to a file and read that
instead.

### `ampx sandbox` is a watcher, not a one-shot deploy

There is no `--once` flag. Any iterate-and-redeploy loop must stop the prior instance first —
or better, leave one watcher running and let it pick up file changes, which is what it is
designed for.

### A fresh clone reports one TypeScript error

`.amplify/generated/env/*.ts` is generated by Amplify during CDK synth and is gitignored. On
a fresh clone, `tsc` reports the `$amplify/env/*` imports as unresolved until the first
sandbox run. **That is expected, not a bug.**
